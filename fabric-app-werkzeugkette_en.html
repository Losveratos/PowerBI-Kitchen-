Fabric App Toolchain

This is how Daten-WG builds its Fabric apps and Power BI reports: a sketch becomes a spec, the dwg cli turns the spec into a Fabric app, a Power BI report or both with the same visuals, and every delivery is checked before an audience sees it. The data comes from an existing source or is generated synthetically for a demo.

Why it works this way

One spec, one or two targets

The same file produces only a Fabric app, only a Power BI report, or both. When both are built, they show the same numbers with the same visuals, and nobody maintains two reports side by side.

Same command, same result

Every step is a CLI call instead of clicks in the portal. An agent can plan it, a person can follow it, and tomorrow the same thing comes out.

Notation as a guardrail

ChartKitchen and P&L bring scenario notation, scaling and templates. Even an app built quickly follows a consistent notation.

Checking is part of the chain

Parity, service queries, test bench and governance run before an audience sees anything. Findings turn into releases instead of surprises.

1

Prepare

What the page should show and where the numbers come from.

MockupKitchen

ours · on this website
Does
Mockups for Power BI pages and Fabric apps in the browser: more than 60 visual types, app templates, phone layout, colour schemes, visual setup.
Where
Right at the start, in the conversation with the business team, before a single line of code exists.
Why
Pages should be agreed before anything is built. Changing a mockup takes minutes, changing code takes hours.
Benefit
The business team sees the result early. dwg mockup import turns the sketch into a spec.

Data source

existing or generated
Does
Delivers the numbers. Usually an existing lakehouse, warehouse or semantic model. For demos, Python with pyarrow generates synthetic data as Parquet, plus control totals for the sums.
Where
In a project, the customer's source; in the examples, the showcase and the demos from the talks.
Why
The chain does not depend on a particular source. The dwg cli only needs a semantic model with measures and columns.
Benefit
The same path for real data and demos. Demos never show customer data and can be regenerated at any time.
2

Building blocks

Spec, visuals and semantic model.

App spec (JSON)

ours · part of the dwg cli
Does
Describes pages, tiles, roles (measures and columns), filters, formats, navigation and the template for each tile.
Where
In the specs/ folder of the dwg cli, for example the showcase spec with 47 pages.
Why
One file that people and agents can read. The command decides which target is built: dwg app page, dwg pbip pages or both.
Benefit
Versioned in Git; dwg check validates it against the model before the build.

ChartKitchen byDatenWG

ours · 1.58.0.0
Does
Custom visual with 14 chart modes and 24 templates (C01 to C25): columns, bridges, tables, scatter, KPI cards, small multiples, with scenario notation and scaling.
Where
In Power BI and, unchanged, in the Fabric app.
Why
Standard visuals do not come with scenario notation and shared scaling. The templates are inspired by IBCS.
Benefit
One visual for both worlds, the same rendering in app and report.

P&L Statement byDatenWG

ours · 1.8.4.0
Does
Income statements and financial tables: account hierarchy, formula rows, Δ columns with pins, 23 templates, ROI tree, Sankey, balance sheet and cash flow.
Where
On every P&L and table page in app and report.
Why
A financial table with variances is a lot of manual work in standard Power BI and looks different in every report.
Benefit
Pick a template instead of formatting; numbers stay the same, the notation is right.

fab · Fabric CLI

used · Microsoft
Does
Workspaces and folders, uploads to the lakehouse, table load, import of model and report, refresh, rebind.
Where
When setting up every demo environment and when delivering.
Why
Everything by command instead of clicks in the portal.
Benefit
Scriptable, the same steps for every environment, traceable in the log.

te · Tabular Editor CLI

used · Tabular Editor · preview
Does
Loads semantic models as TMDL, validates them (te validate), changes them by script, queries them.
Where
New models such as the showcase's Direct Lake model, and just as well an existing model that an app is put on top of.
Why
Numbers and formats come from the model; the dwg cli reads them from there.
Benefit
Model changes as text, validated before deployment.
3

Generate

The building blocks become an app, a report or both.

dwg cli

ours · public · early preview
Does
Builds the Fabric app pages (React), the report as PBIP/PBIR, or both from spec and model. Generates the DAX queries, binds the visuals, pulls in new releases with visuals update, tests with mini-DAX in the browser without Fabric, checks with dwg check and dwg lint.
Where
In the showcase with 47 templates and in the live demo of the Data Bash talk.
Why
Fabric apps have no report canvas, so every page would be handwork in React. And where both exist, Power BI should show exactly the same.
Benefit
Same spec, same result. One command brings a new visual release into the CLI; app and report are then regenerated from it.

Parity test

ours · in the dwg cli
Does
Renders each tile the way Power BI hands the data to the visual and the way the app does, and fails if the two differ. Runs locally with mini-DAX, before delivery.
Where
Only when app and report come from the same spec on the same semantic model, for example in the showcase on every test run. With only an app or only a report it does not apply.
Why
Two targets from one spec are only worth something if they really are the same.
Benefit
Differences show up while building, not at the customer.
4

Deliver

The targets land in Fabric.

Rayfin CLI · Fabric apps

used · Microsoft · preview
Does
Creates the Fabric app item and deploys it (rayfin up), binds connectors to the semantic model, provides hosting and Entra sign-in.
Where
For every Fabric app, for example the showcase app.
Why
The scriptable way to create and deploy a Fabric app. The Fabric REST API cannot do it.
Benefit
Backend, sign-in and hosting come from Fabric; the app reads the model directly.

pbir CLI

used
Does
Checks and changes PBIR reports, binds them to the model (rebind), tests every visual query against the service.
Where
After publishing the report; in the showcase 282 of 282 queries without errors (as of 25 Nov 2026).
Why
Editing report JSON by hand is error-prone.
Benefit
The CLI finds errors in the report, not the audience.

Git and GitHub

used
Does
Spec, PBIP and visual code live in Git. GitHub Actions run the tests and the showcase run on every change. Fabric Git integration is the second route for the report next to fab import.
Where
dwg cli, visuals, website.
Why
Every change should be visible, testable and reversible.
Benefit
Releases with a pull request and green tests instead of copies on a drive.
5

Check

Before an audience sees it.

Template test bench

ours
Does
Checks each template element by element against the reference and puts Fabric app and Power BI side by side, with measurements of load time, queries and load.
Where
For all 47 showcase templates, 39 of them with a reference.
Why
"Can be built" should be measured, element by element.
Benefit
The findings become the wave plan. Wave 1 delivered ChartKitchen 1.58 and P&L 1.8.4.

fabscan

ours · CLI and skill
Does
Governance check for Fabric apps: calculations in the app, lineage, security (app identity, external servers, external fonts), modified queries and deviations from the model.
Where
Across the demo apps and the dwg cli output; findings flow back into the dwg cli.
Why
AI builds apps fast. Someone has to check what they load and what they access.
Benefit
Findings with a stable ID, exceptions with a reason, coverage in the report.

Playwright

used · Microsoft
Does
Browser tests and screenshots for visuals, apps and documentation pages.
Where
Visual self-tests, showcase run, test bench images.
Why
Compiled does not mean drawn correctly.
Benefit
The actual rendering is proven, down to the details of the notation.
∞

Above it all

Who plans, builds and approves.

Claude Code · Fable

used · Anthropic
Does
Sessions plan and build in parallel, one each for data, frame and templates. Skills for dwg, fabscan and mockups teach the agents the commands. Fable reviews independently.
Where
In every phase, steered from a coordinating session.
Why
Speed with the same care.
Benefit
The agent plans, the CLI executes, the check verifies. A person approves push, merge and deployment.
